# 클라이언트 모드와 간편 패키지 배포 검토

작성일: 2026-11-02 · 상태: **모드 필수 정책 확정 / 구현·접속 강제 전환 전**

## 1. 결론

**Paper 서버 플러그인을 유지하면서 전용 Fabric 클라이언트 모드와 모드팩을 추가하는 방식을 권장한다.** 현재 가장 큰 불만인 상점·램프·토지 UI를 개선하는 데 직접적인 효과가 있다. 참가자에게 개별 모드 파일을 수동으로 넣게 하지 말고, 검증된 버전을 묶은 모드팩을 가져오게 한다.

**2026-11-02 사용자 결정: 전용 클라이언트 모드는 필수로 한다.** 연결·설치·주요 화면 검증을 마친 후 운영 서버에 적용한다. 선택 설치를 정식 운영 정책으로 유지하거나 필수 여부를 다시 결정하는 단계는 두지 않는다.

전환 전 기존 UI는 개발·비교·복구용으로만 유지한다. 모드 화면으로 교체된 기능은 전환 완료 후 기존 화면의 신규 디자인 개발을 중단한다. 모든 기능이 옮겨지기 전에는 미전환 기능의 기존 화면을 모드 사용자에게도 사용할 수 있게 유지한다. 공통 서버 서비스와 데이터는 계속 공유한다.

배포 규모·공개 범위·서버 주소·최종 설치 방식·첫 구현 대상·새 UI의 표현 범위는 아직 별도 확정하지 않았다. 아래 `.mrpack` 권장안과 단계는 제안이며, 이번 결정이 자체 런처 개발이나 서버 공개를 승인한 것은 아니다.

이전 `docs/PLAN.md`의 ‘클라이언트 모드는 쓰지 않는다’는 현재 구현 설명으로 남기되, 앞으로의 개발 선택지를 제한하는 원칙으로 사용하지 않는다.

## 2. 먼저 구분할 것: 운영자 배포와 참가자 배포

현재 소스에서 확인한 내용:

- `pom.xml`: Paper 1.21.11, Java 21, MaiTycoon 0.22.0.
- `scripts/package.sh`: 플러그인 JAR, 서버 시작 파일, 안내서·문서를 운영자용 ZIP으로 묶는다.
- `distribution/설치안내.md`: 일반 참가자는 Java Edition 1.21.11로 서버에 접속하며 모드 설치가 필요 없다.
- 리소스팩은 서버에서 제공한다. 현재 UI는 인벤토리 슬롯, 폰트 그림, 보스바 등을 이용한다.

**현재 모든 참가자에게 실행 스크립트를 줄 필요는 없다.** 모드를 도입하면 참가자용 설치·업데이트 배포물이 새로 필요하다. 서버 ZIP과 클라이언트 모드팩을 같은 파일로 섞지 않는다.

| 대상 | 제공물 | 목적 |
|---|---|---|
| 서버 운영자 | 서버 starter ZIP 또는 plugin JAR | Paper 서버 운영, 월드·경제·권한 저장 |
| 일반 참가자 | 클라이언트 `.mrpack` + 짧은 설치 안내 | 전용 UI·HUD·조작·렌더링 설치 |
| 개발자 | 서버/클라이언트 소스와 테스트 지침 | 기능 개발 및 프로토콜 검증 |

## 3. 실제로 넓어지는 선택지

Fabric 1.21.11 문서는 독립적인 Screen과 위젯을 만드는 방법을 제공한다. 따라서 상자 슬롯과 폰트 그림의 배치에 얽매이지 않는 UI를 개발할 수 있다. 아래 적용 예시는 해당 기능을 바탕으로 한 **우리 프로젝트 설계 제안**이다. [Fabric Custom Screens](https://docs.fabricmc.net/1.21.11/develop/rendering/gui/custom-screens)

| 기능 | 현재 방식의 제약 | 전용 클라이언트에서 구현할 내용 | 서버에 남길 책임 |
|---|---|---|---|
| 상점 | 슬롯에 맞춘 카드·버튼, hover 의존 | 자유로운 카드 배치, 검색, 스크롤, 수량 입력, 거래 확인창 | 실제 가격·재고·잔액 계산, 지급 |
| 램프 | 인벤토리 화면으로 대상과 결과 표현 | 도구 미리보기, 현재/새 능력 비교, 결과 애니메이션 | 무작위 결과·소비·저장 |
| 토지 | 청크가 아이템처럼 보임 | 확대/축소 지도, 선택 강조, 경계 오버레이, 상세 패널 | 소유권·가격·권한·매입 재검증 |
| 농장 관리 | 아이콘과 lore에 정보 분산 | 작물별 목록, 성장 상태, 작업자 편집 화면 | 성장 시간·허용 작업·멤버 수정 |
| HUD·지도 | 보스바 위치·문자 폭 제약 | 고정 패널, 배율·위치 설정, 지도·잔액·알림 분리 | 공개 가능한 상태만 전달 |
| 커스텀 작물 | 기본 블록/아이템 표현에 맞춤 | 성장 단계별 렌더링·흔들림·선택 표시 | 재배·성장·수확·충돌 판정 |
| 펫·탈것 | 서버 엔티티와 팩 기반 표현 | 커스텀 외형·애니메이션·카메라·보관함 | 획득 확률·소유·탑승·이동 검증 |
| 조작 | 기존 키·채팅 링크 활용 | 설정 가능한 전용 단축키, NPC 메뉴, 안내 패널 | 행동 가능 거리·상태 확인 |

램프의 효과와 펫 뽑기 결과는 서버가 먼저 결정한다. 클라이언트는 전달받은 결과를 연출한다. 연출을 건너뛰거나 연결이 끊겨도 결과가 달라져서는 안 된다.

### 모드가 있어도 자동으로 해결되지 않는 것

- UI를 그릴 자유가 생기는 것이며 좋은 레이아웃·그림·한글 가독성은 별도로 설계해야 한다.
- Paper에 Fabric 모드 JAR을 넣어 실행할 수 있는 것은 아니다. **Paper 플러그인과 Fabric 클라이언트 모드는 별도 산출물**이다. [Paper 플러그인 설치 안내](https://docs.papermc.io/paper/adding-plugins/)
- 진짜 신규 블록/엔티티의 서버 레지스트리, 새로운 물리·월드 생성은 클라이언트만으로 추가되지 않는다. 우선 기존 서버 표현을 전용 렌더러로 보강한다.
- 완전히 새로운 서버 콘텐츠 체계가 필요해지면 Fabric 서버 전환을 별도 검토한다. 그 경우 Bukkit/Paper 코드의 이식 비용이 발생한다.
- 모드 설치만으로 서버 렉이나 거래 저장 문제가 해결되지는 않는다. 성능·데이터 무결성은 별도 작업이다.
- 원본 띵타이쿤이 같은 모드 구조였다고 확인한 것은 아니다. 이번 제안은 원하는 경험을 구현하기 위한 선택이다.

## 4. 아키텍처 권장안

```text
참가자 PC
  기존 런처 → Minecraft 1.21.11 + Fabric
               └ Mai Tycoon Client
                  UI / 입력 / HUD / 표현
                         ↕ 버전이 있는 전용 payload
Paper 1.21.11
  MaiTycoon plugin
    통신 어댑터 → 공통 서비스 → 경제·토지·농사·램프·펫 저장
    기존 인벤토리 UI ────────┘
```

Paper는 플러그인 메시지를 통한 클라이언트 통신을 제공하며, Fabric은 custom payload 송수신을 제공한다. 이를 이용한 연결을 권장하지만, **둘의 예제를 각각 붙이면 자동 호환되는 것은 아니다.** 채널 ID, payload 바이트 순서, 길이 제한, 등록 시점과 수신 스레드를 맞춘 작은 실증 구현이 먼저 필요하다. Paper 문서의 BungeeCord 예제를 우리 채널 규격으로 오해하지 않는다. [Paper Plugin messaging](https://docs.papermc.io/paper/dev/plugin-messaging/), [Fabric 1.21.11 Networking](https://docs.fabricmc.net/1.21.11/develop/networking)

### 책임 분리

- 서버: 통화, 가격, 판매량, 구매, 땅, 램프 옵션, 작물 성장, 펫 소유의 최종 권한.
- 클라이언트: 화면 표시, 수량/대상 선택, 확인 요청, 애니메이션.
- 공통 프로토콜: 기능 ID, 요청/응답 필드, 오류 코드, 버전 규칙. 서버 Maven·클라이언트 Gradle 간 코드 공유 없이 규격 문서와 동일한 테스트 데이터로 codec 일치를 검증한다.
- 기존 UI와 모드 UI 모두 같은 서버 서비스 호출. 거래 처리를 두 벌로 만들지 않는다.
- `Lamps`, `Lands`, `Shop`의 GUI 이벤트 안에 결합된 처리부터 서비스로 분리한다. YAML 저장 형식이나 기존 재산을 이번 UI 전환 때문에 초기화하지 않는다.

### 최초 통신 실험

1. 접속 후 `hello`: 모드 버전, protocol major/minor, 지원 기능 목록.
2. 서버 `hello_ack`: 호환 여부, 허용 기능, 서버 표시 이름, 세션 정보.
3. NPC 우클릭 → 서버가 거리·상태 확인 → `open_lamp_shop` 스냅샷 전송.
4. 모드 화면에서 상품·보유량·서버 가격 표시.
5. 램프 `buy_request`: requestId, 상품 ID, 수량. 램프는 설정의 고정 가격을 서버가 검증한다. 변동 시세 상점에는 별도로 quoteId/revision을 적용한다. 클라이언트가 가격·UUID·잔액을 확정하지 않는다.
6. 서버가 동일 서비스를 통해 거래 검증·저장 후 결과와 최신 잔액 전송.
7. 실패는 이유를 표시하고 구매 버튼을 다시 활성화. 시간 초과는 ‘결과 확인 중’으로 처리하고 무조건 재구매하지 않는다.

기존 TransactionJournal과 WalletLog를 재사용한다. 추가 구현 대상은 요청 ID 기반 중복 방지, 기존 거래와의 연결, 재접속 후 결과 조회다. UI를 추가했다는 이유로 현재 저장 방식이 원자적이라고 가정하지 않는다. 세션 토큰이나 handshake는 정품 모드의 증명이 아니므로 모든 요청을 서버에서 검증한다.

NPC 세션 만료, 거리 이탈, 음수·과도한 수량, 가격 갱신, 순차 처리 중 다른 사용자가 먼저 산 땅의 소유권 재확인, payload 길이 초과, 연타를 서버에서 처리한다. 지도 데이터도 현재 정책상 공개 가능한 범위만 보낸다.

## 5. 설치 패키지 방식 비교

| 방식 | 사용자 설치 경험 | 우리 유지보수 | 판단 |
|---|---|---|---|
| JAR만 제공 | 로더·API·폴더·버전 직접 맞춤 | 문의가 많아짐 | 개발자 테스트용 |
| 기존 런처 + `.mrpack` | 런처 설치/로그인 후 팩 가져오기 | 버전 묶음과 안내 관리 | **1차 권장** |
| 공식 런처 + 보조 설치 스크립트 | 로더 설치·별도 프로필 설정 필요 | OS별 경로·실행 권한·프로필 관리 | 대안, 후순위 |
| 자체 전용 런처 | 성공하면 맞춤 경험 제공 | 인증·다운로드·업데이트·서명·OS 지원까지 담당 | 사용자 규모와 필요 확인 후 |
| 서버까지 Fabric 전환 | 참가자·운영자 모두 모드 환경 | 기존 서버 코드 이식 필요 | 현재 UI 문제 해결 범위를 넘음 |

`.mrpack`은 Minecraft/로더 의존성과 파일 다운로드 주소·해시, overrides를 기술하는 ZIP 기반 모드팩 형식이다. 독립 실행 프로그램이 아니며 가져오기를 지원하는 런처가 필요하다. 모드 다운로드와 설치 자동화에 적합하지만 실행 중인 게임의 무중단 모드 업데이트를 보장하지 않는다. [Modrinth 모드팩 규격](https://support.modrinth.com/en/articles/8802351-modrinth-modpack-format-mrpack)

초기 안내의 기준 런처는 **Prism Launcher**로 제안한다. 공식 문서에서 Import를 통한 `.mrpack` 가져오기를 안내하고 있다. 여러 런처를 동시에 지원 대상으로 선언하지 말고 한 가지 경로부터 깨끗한 PC에서 검수한다. [Prism 모드팩 가져오기](https://prismlauncher.org/wiki/getting-started/download-modpacks/)

## 6. 사용자에게 제공할 설치 흐름

목표 흐름이며 아직 배포 파일은 만들지 않았다.

1. 안내 페이지에서 지원 OS, 정품 Java Edition 필요, 팩 버전 확인.
2. 기준 런처 공식 배포처 설치 및 런처가 제공하는 Microsoft 로그인 사용.
3. 제공받은 `mai-tycoon-client-<packVersion>.mrpack` 가져오기.
4. 런처가 고정된 Minecraft·Fabric·필요 모드를 내려받고 별도 인스턴스를 생성.
5. `Mai Tycoon` 인스턴스 실행 → 전용 시작 화면의 서버 접속 버튼 이용.
6. 첫 접속 안내에서 상점 NPC, 도움말의 토지 메뉴, 단축키를 소개한다. 현재 토지 NPC는 없다.

첫 설치는 런처 설치·로그인·다운로드가 있으므로 ‘파일 한 번 클릭하면 끝’이라고 홍보하지 않는다. 두 번째 실행부터 간단해지는 경험을 목표로 한다. 서버 접속 버튼과 주소 표시도 우리 모드에서 구현해야 하는 항목이다.

### 스크립트의 역할

선택적인 진단/안내 도구로 제한한다. Java/OS/팩 버전 확인, 공식 다운로드 안내, 진단 로그 정리 정도를 우선한다. 사용자의 기본 `.minecraft`에 임의로 덮어쓰거나 기존 `options.txt`, saves, 다른 모드를 삭제하지 않는다. 별도 인스턴스만 관리한다.

게임 JAR·Microsoft 계정 토큰·비밀번호·개인 서버 주소록·개발 월드·개인 로그는 패키지에 넣지 않는다. 게임 본체는 런처의 정식 다운로드 경로를 이용하고, 외부 모드·폰트·이미지는 각 라이선스와 배포 조건을 확인한다. 자체 제작 모드와 수정 게임 본체 배포는 구분해야 한다. [Minecraft EULA](https://www.minecraft.net/en-us/eula)

```text
  CHANGELOG.md
  SHA256SUMS
  licenses/
```

제안 저장소 구성:

- 기존 Maven 서버 프로젝트 유지.
- `client/`: Fabric Loom 기반 클라이언트. 서버 Maven에 억지로 합치지 않는다.
- `protocol/`: 메시지 규격 문서·공통 테스트 데이터. 공유 Java 모듈은 초기 범위에서 제외한다.
- `distribution/client/`: 팩 인덱스 템플릿과 설치 문서.
- `scripts/package-client.*`: 검증된 결과만 포장하는 새 명령. 기존 `package.sh`는 서버용으로 유지.

초기 기준은 현재 프로젝트의 **Minecraft 1.21.11 / Java 21**이다. Fabric Loader와 Fabric API의 구체 버전은 호환 실험 후 고정한다. 최신 문서의 26.x 코드를 그대로 가져오지 않고 1.21.11 문서를 기준으로 한다. 목표 버전이 지원 종료되면 별도의 업그레이드 작업으로 처리한다.

`COMPATIBILITY.md`에는 Minecraft, Java, 서버 플러그인, 클라이언트 모드, Loader, Fabric API, protocol major/minor, 자산 버전을 함께 기록한다. 현재는 클라이언트 조합이 검증되지 않았으므로 설치 가능한 완성 조합처럼 표기하지 않는다.

## 8. 업데이트·복구 정책

- 모드/로더 업데이트는 게임 종료 후 적용. 접속 중 JAR 교체 금지.
- 패키지별 정확한 의존 버전과 해시 고정. 최신 버전 무조건 다운로드 금지.
- 새 팩은 별도 인스턴스로 시험하고 이전 팩을 롤백용으로 보관한다.
- 사용자 키 설정·스크린샷·접근성 설정을 새 기본값으로 덮어쓰지 않는다.
- 서버가 허용하는 protocol 범위와 맞지 않으면 알기 쉬운 업데이트 안내. 필수 운영 모드에서는 정상 세션 시작 전 접속을 제한한다.
- 개발 서버에서만 임시 fallback을 허용한다. 필수 운영 전환 후에는 handshake 미수신·비호환 클라이언트에 설치/업데이트 안내를 제공하고 세션을 종료한다. handshake 대기 중 거래·이동·상호작용을 허용하지 않는 진입 제어를 검증한다. custom payload 교환 전 로그인 단계에서 모드 유무를 반드시 판별할 수 있다고 가정하지 않는다.
- 클라이언트 롤백은 서버 데이터 롤백과 별개다. 서버 스키마 변경이 있으면 이전 클라이언트 호환 여부부터 판단한다.
- `.mrpack` 배포만으로 자동 업데이트 서비스가 생기지는 않는다. 초기에는 새 팩 가져오기 안내, 이후 배포 채널의 업데이트 기능을 검증한다.
- 화면 자산은 모드 내장과 서버 리소스팩의 담당을 분리한다. 같은 이름의 텍스처를 양쪽에서 다른 버전으로 제공하지 않는다.

## 9. 단계별 실행 계획과 완료 조건

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| P0 연결 실증 | Fabric 클라이언트 생성, Paper payload handshake·왕복 | 실제 1.21.11 클라이언트와 Paper에서 요청/응답, 모드 미설치·버전 불일치의 안내 및 제한 경로 검증 |
| P1 램프 수직 구현 | NPC→전용 상점→구매→적용→결과 | 실제 계좌·옵션과 화면 일치, 중복 요청·고정 가격 검증·재접속 처리 |
| P2 설치 패키지 | 최소 모드팩, 한국어 안내, 격리 인스턴스 | Windows 및 macOS에서 개발 도구 없이 설치·로그인·접속 성공 |
| P3 토지·상점 | 지도 선택/확인, 상품 검색/수량·거래 확인 | 기존 서비스와 같은 권한·거래 결과, 명령어 없이 완주 |
| P4 HUD·작물·펫 | 잔액/지도 통합, 커스텀 렌더링·연출 | 저사양 성능·GUI 배율·키 충돌·다른 화면 복귀 검수 |
| P5 필수 운영 전환 | 설치·주요 화면·호환성 검증 후 운영 반영 | 미설치 접속 제한, 업데이트 안내, 복구 절차 확인. 전환된 기존 UI는 유지보수 대상에서 제외 |

첫 배포에는 전용 모드와 꼭 필요한 의존성만 넣는다. 셰이더·음성 채팅·추가 최적화 모드는 각각 목적과 버전 호환성이 검증된 뒤 추가한다.

### 검수 항목

- 신규 PC 설치, 기존 Minecraft 설치와 공존, 공백/한글 사용자 경로, Apple Silicon·Windows 지원.
- 파일 누락/해시 불일치/다운로드 중단/디스크 부족/구버전 팩의 복구 안내.
- GUI 배율 2/3/4, 작은 창, 긴 한글·큰 금액, 키 재지정, Esc·뒤로가기·채팅 복귀.
- 모드 미설치/버전 불일치/서버 이동 시 세션과 HUD 정리.
- 램프 반복 요청, 돈 부족, 도구 교체, 토지 선점, 메뉴를 연 뒤 이동, 서버 종료 직전 요청.
- 클라이언트 숫자 조작이 서버 잔액·확률·권한에 영향을 주지 않음.
- 설치·업데이트·롤백은 문서만 검토하지 않고 실제 사용자 역할로 진행.

## 10. 기존 요구와의 관계

돈은 서버 계좌 잔액이며 아이템 소지가 필요 없다. 상점은 NPC/메뉴로 접근하고 관리자 명령어는 유지한다. 시세는 사용자 요청의 무작위 변동과 판매량 영향 정책을 유지한다. 펫 S등급 1% 등 게임 규칙도 서버가 책임진다.

이번 제안의 우선 목적은 **램프·토지·상점을 원하는 품질로 만들 수 있는 화면 기반을 확보하는 것**이다. 먼저 램프 한 화면과 실제 거래를 완성하면 모드팩 설치 부담에 비해 얻는 이익을 구체적으로 평가할 수 있다.

이번 작업에서는 모드·설치기 구현, 외부 업로드, 참가자 배포, 서버 설정 변경을 하지 않았다.

## 11. 결정 후 인계 사항

- 확정된 사항은 **검증 후 모드 필수 운영**이다. 모드가 아직 없으므로 현재 서버에서 참가자를 즉시 차단하지 않는다.
- M 키 전체 지도로 P0 통신을 검증하자는 제안은 유효하다. 다만 로컬 화면만 여는 것으로 통신 검증을 끝내지 말고 실제 서버 지도 응답과 재접속·불일치 처리를 포함해야 한다. 우선순위 확정 전까지 기존 단계표는 제안으로 취급한다.
- 소규모 지인 테스트는 Fabric 설치 안내 + 전용 JAR 및 필요한 의존성으로 시작할 수 있다. Fabric API가 필요하면 JAR 하나만으로 충분하다고 안내하지 않는다. 간편 설치 요구에 맞춰 수동 방식과 모드팩의 실제 설치 시간을 비교한다.
- 사설 서버 주소와 참가자 접속 정보는 공개 소스/팩에 하드코딩하지 않는다. 사용자 입력 또는 비공개 설정으로 분리한다. 공개 운영 여부는 미정이다.
- Windows 설치 검증은 실제 Windows 환경에서 수행해야 한다. Mac 테스트나 개발용 클라이언트 접속을 정품 계정·Windows 접속 검증으로 보고하지 않는다.
- Village.java/VillageBuilder.java의 상점 재설계는 이 작업의 기존 변경이다. 2026-11-01 서버 로그에서 재생성을 확인했고, 현재 village.yml도 structures=7이다. **미커밋이라는 이유만으로 미배포라고 판단하지 않는다.** 배포 내역은 ../village/SHOP-REDESIGN-2026-11-01.md 참고.
