# 방송용 띵타이쿤 재화·거래 조사와 적용 설계

조사·수정: 2026-11-01. 대상: **2024년 방송용 원본 띵타이쿤**.
상태: 0.17.0에 지갑 조회와 온라인 대상 골드 송금 적용. 직업 코인·펫 티켓은 해당 기능이 생길 때 연결.
표시 이름은 사용자 지시에 따라 골드·즈코인을 유지합니다. 아래의 YD·띵코인은 원본 이름입니다.
최신 사용자 요구: **돈을 아이템 형태로 들고 다닐 필요가 없어야 한다.** 아래 계정 지갑 규칙은 원본의 물리 아이템 사용 여부와 관계없이 우선 적용합니다.

## 1. 조사 결론과 신뢰 범위

공개된 원본 설명과 당시 커뮤니티 기록에서는 YD, 띵코인, 직업 코인을 구분합니다. 다만 이번 조사에서 원본 운영 문서나 실제 송금 장면을 직접 검증하지 못했습니다. **재화 구분을 참고할 근거는 있지만 송금 키·거리·수수료까지 원본과 같다고 확정할 근거는 부족합니다.**

| 구분 | 확인한 내용 | 근거 / 판정 |
|---|---|---|
| 기본 돈 | 기본 화폐 YD, 상점 판매 및 유저 간 거래 등으로 획득 | S1 경제 절, 2차 자료 |
| 별도 코인 | 직업 코인과 띵코인이 따로 존재하며 직업 코인 조합으로 띵코인 획득 | S1 경제 절, S2 당시 요약으로 교차 확인 |
| 상점 시세 | 판매가 10분 주기 변동, 상한·하한 존재 | S1 경제 절 |
| 펫 결제 흐름 | 펫 뽑기 상점에서 펫 티켓을 구매해 이용 | S1 펫 절 |
| 티켓 보상 | 도감 50개 보상에 펫 티켓 포함 | S1 도감 절, S3 당시 로드맵 |
| 특수 소비 | 히든 상점에 띵코인 결제 품목 존재 | S1 히든 상점 절 |
| 미확인 | YD 송금 UI/명령어, 거래 거리, 수수료, 수표 발행, 오프라인 송금, 직업 코인의 정확한 조합식, 펫 티켓 구매 재화·가격·회당 소모량 | 확정 규칙으로 구현하지 않음 |

사용자가 앞서 제공한 상점 스크린샷에도 YD 표기가 있습니다. 단일 정지 화면만으로 실제 차감 과정이나 유저 간 송금 방법까지 확인한 것으로 간주하지 않습니다.

## 2. 적용할 재화 모델 — 모두 계정 지갑

| 항목 | 목표 표시 이름 | 보관 방식 | 사용 원칙 |
|---|---|---|---|
| 일반 돈 | YD | UUID별 정수 잔액 | 상품 구매/판매·일반 대금 |
| 특수 코인 | 띵코인 | 일반 돈과 분리한 정수 잔액 | 지정된 특수 상품/성장 기능 |
| 직업별 코인 | `<직업명> 코인` | 직업 ID별 정수 잔액 | 직업별 획득·교환, 직업 기능 구현 후 연결 |
| 펫 티켓 | 펫 티켓 | 계정별 이용권 수량 | 추첨 이용권. 지갑과 별도 카운터 |

**주머니에 동전·지폐·수표를 넣어둘 필요가 없습니다.**

- 돈을 손에 들지 않아도 구매·판매·송금 가능.
- 돈·코인은 인벤토리 칸, 상자 공간, 아이템 최대 스택을 사용하지 않음.
- 지급은 계정 잔액 증가, 사용은 잔액 차감. 버리기·줍기·사망 드롭의 대상이 아님.
- 계정 저장값이 유일한 잔액 원본. GUI의 동전 아이콘은 표시용이며 실제 돈 아이템으로 꺼낼 수 없음.
- 전용 지갑 메뉴에서 재화별 잔액과 최근 거래를 조회. 기존 도움말/NPC 메뉴에서 접근하며 새 필수 소지 아이템이나 F 키 충돌을 만들지 않음.
- 각 재화는 정수로 계산. 음수·소수 입력·범위 초과는 거절하고, 오버플로도 검사.
- YD와 띵코인 사이의 고정 환율은 근거 없이 만들지 않음.
- 직업 코인 조합은 정확한 종류·소모 수량을 추가 확인한 뒤 지갑 차감/지급 방식으로 구현. 물리 제작대 조합을 강제하지 않음.
- 펫 티켓도 종이 아이템 보유를 요구하지 않는 계정 이용권으로 설계. 이는 사용자 편의 요구를 반영한 프로젝트 결정임을 표시.

## 3. 거래별 처리 흐름

### NPC 구매·판매

구매: NPC → 상품/수량 → 결제 재화와 합계 표시 → 지갑 잔액/수령 공간 재검사 → 잔액 차감과 상품 지급 → 결과 안내.
판매: 판매 가능한 상품/수량 확인 → 시세 견적 → 상품 회수와 YD 증가 → 공급량 집계.
실물 상품을 받는 공간 검사는 계속 필요하지만, 돈을 받기 위한 빈 인벤토리 칸은 필요하지 않습니다.
같은 상품이 서로 다른 재화를 요구할 수 있으므로 상품 데이터에 `currency`를 명시하고, 코인 아이콘만으로 결제 재화를 구분하지 않습니다.

### 유저 간 YD 송금 — 동작 설계 제안, 원본 조작 미확인

지갑 메뉴 → 대상 계정 선택 → 수량 입력 → 대상·보내는 금액·받는 금액·수수료·송금 후 잔액 확인 → 확정 → 두 계정에 결과 표시.

- 기본은 YD 송금부터. 온라인 수신자만 지원하는 최소 구현안을 제안하되, 원본 규칙이라고 표기하지 않음.
- 수수료와 거리 제한은 미확정. 온라인판의 5%/30칸을 기본값으로 가져오지 않음. 검증 전 테스트 환경은 무수수료로 가능하나 공개 규칙은 자료 확인 후 결정.
- 받는 사람은 UUID로 저장. 표시명 변경, 자기 자신, 존재하지 않는 계정, 수신자 접속 종료를 확인.
- 물건과 맞교환하는 안전 거래가 아니라 순수 송금이라는 점을 화면에 구분. 송금만으로 상품 인도를 보장한다고 표시하지 않음.
- 상점 명령어 관리자 전용 원칙은 유지. 유저 송금은 지갑 메뉴에서 가능하며 별도 명령어 필요 여부는 후속 결정.
- 직업 코인/띵코인 거래와 물품 맞교환 GUI는 별도 단계. 양쪽 수락 후 내용이 바뀌면 수락을 모두 취소하고 다시 확인하도록 설계.

## 4. 펫 가챠 계획 정정

기존 `펫 1회 = 골드 3,000 직접 차감`은 자체 테스트 제안이었으며 원본 재현 가격이 아니었습니다. 이를 **티켓 구매 → 계정 이용권 보관 → 티켓으로 뽑기** 구조로 바꿉니다.

- 원본에서 펫 티켓 구매 흐름은 2차 자료로 확인. 구매에 쓰는 돈/코인의 종류와 가격은 미확인.
- 확인 전 티켓 판매는 비활성. 관리자 테스트 지급으로 추첨·저장·연출을 검증.
- 추첨당 티켓 1회 사용은 프로젝트 시제품 제안값이며 원본 회당 소모량으로 단정하지 않음.
- 도감 50개 펫 티켓 보상을 연결하되 기존 달성자의 중복 보상/누락은 별도 이행 정책으로 처리.
- 티켓 구매와 추첨은 서로 다른 거래 ID. 추첨 실패 시 이미 정상 구매한 티켓을 다시 판매하거나 돈으로 자동 재환급하지 않음.
- 추첨은 티켓 차감과 펫/중복 조각 지급을 함께 추적. 재접속으로 재추첨하지 않음.
- **사용자가 확정한 S 1%는 유지**. 화폐 조사로 확률·라인업·속도를 변경하지 않음.

## 5. 현재 구현과의 차이 및 이행

현재 [ProfileStore](../../src/main/java/kr/maitycoon/ProfileStore.java)는 UUID별 파일의 `coins`, `zcoin`으로 잔액을 저장하므로 일반 돈과 즈코인은 이미 실물 소지가 필수가 아닙니다. 새로 필요한 부분은 재화 명칭 정합성, 직업별 지갑, 티켓 잔액, 유저 간 거래입니다.

| 현재 | 문서상 목표 | 이행 원칙 |
|---|---|---|
| 골드 / `coins` | YD / 일반 지갑 | 잔액 수량 보존, UI 명칭부터 변경. 가격 배수 변경이나 초기화 없음 |
| 즈코인 / `zcoin` | 띵코인 / 특수 지갑 | 기존 획득·소비 내역을 점검한 뒤 1:1 수량 보존. 원본 환율 주장 아님 |
| 직업별 잔액 없음 | 직업 코인별 잔액 | 초기 0, 아직 없는 직업 보상을 임의 지급하지 않음 |
| 펫 골드 직접 결제 계획 | 계정 펫 티켓 소비 | 미구현 계획 수정, 미확인 판매가를 적용하지 않음 |
| 상품별 테스트 가격 | 근거 있는 가격만 원본값 지정 | 나머지는 개발용 표시 유지 |

다른 개발 세션이 현재 경제 코드를 수정 중이므로 구현 시작 전 재확인합니다. 이번 문서 변경만으로 `coins`/`zcoin` 키나 서버 잔액을 수정하지 않습니다.
이행 버전과 완료 표시를 저장하고 재실행해도 잔액이 중복 합산되지 않아야 합니다. 기존 파일을 백업하고 변경 전후 전체 재화 합계를 비교합니다.

## 6. 저장·복구 및 완료 조건

- 모든 결제/송금에 거래 ID, 계정 UUID, 재화 ID, 전후 잔액, 상태를 기록.
- 유저 간 송금은 두 계정 동시 변경이므로 기존 단일 플레이어 거래 함수를 단순히 두 번 호출해서 완료했다고 간주하지 않음.
- 지갑 간 이체에는 양쪽을 원자적으로 저장하는 저장소 또는 재실행 가능한 다중 계정 거래 기록이 필요. UUID 순서 잠금으로 동시 송금 충돌을 방지.
- 실패 지점이 불명확하면 관련 거래를 잠그고 관리자 검토. 무조건 환급과 지급을 둘 다 수행하지 않음.
- 지급량/수수료/차감량을 각각 기록. 무수수료 이체는 두 계정 합계가 보존되어야 함.
- 재화 아이템 출금·수표 발행은 첫 버전에 넣지 않음. 이후 요청되더라도 계정 지갑 사용은 필수 유지.

검증 목록: 인벤토리 빈칸 0에서 판매대금 수령, 빈손 결제, 사망/재접속 후 지갑 보존, 부족한 잔액, 잘못된 계정, 0/음수/초대형 입력, 연타, 동시 양방향 송금, 저장 단계별 강제 실패, 티켓 중복 소비, 구버전 이행 재실행.

## 7. 원본과 동일하다고 표시하기 전 확보할 자료

방송용 원본의 송금 화면/실제 조작 영상, 수수료 표시, 코인 획득·조합 장면, 펫 티켓 구매 화면(재화/가격/수량)을 추가 확보해야 합니다.
현재 확인 수준은 재화 구분과 티켓형 이용 흐름까지입니다. 미확인 규칙은 제안·미정으로 남기고, 사용자 요구인 비실물 지갑은 확정 적용 방침으로 둡니다.
